# AgentCanvas 未来开发方案审查与修订建议

> 日期：2026-09-13。主审对象：[agentcanvas-future-roadmap.md](agentcanvas-future-roadmap.md)，基线日期 2026-09-12。
> 本文是对方案合理性的审查，不覆盖原稿，不实施业务改动。当前工作树包含既有未提交修改。

## 结论

**方向大体合理，但不建议直接把原稿当作执行排期。** 更适合把它视为候选功能库：保留桌面交付、集成体验、受控模板和运行诊断主线；先修正能力基线、共享副作用/契约保证，再重新排期。市场、Saga、CRDT、多语言 SDK 和 SaaS 不能同时成为一个季度的承诺。

建议修订后的主线是：

> **可信的 Windows/自托管交付 → 一个可复用、可审核的真实工作流场景 → 一个稳定的集成入口 → 以实际使用数据决定扩展。**

| 审查维度 | 判断 | 主要理由 |
|---|---|---|
| 产品方向 | **保留，但收敛** | 桌面、开发者接入、模板和生态符合可视化编排产品；同时开市场/企业身份/跨平台过宽 |
| 当前能力基准 | **必须修订** | 向量抽象、队列/连接池、部分重放和编排能力已有；C9 状态及编号与专项计划不一致 |
| 技术合理性 | **部分成立，部分需改设计** | 存在重复基础设施、MCP live-session 迁移、事件顺序、OR-join 和加密概念的边界问题 |
| 优先级与资源 | **不宜原样采纳** | 局部/全局 P 级含义不清；新 SDK/生态扩展排在尚未覆盖的共享安全/契约保证前 |
| 验收与生产承诺 | **证据不足处需降级表述** | 本轮目标测试通过，但离线反例暴露了测试未覆盖的契约与副作用分类；历史性能/生产标签不能替代当前验证 |

## 2. 必须先纠正的能力基线

| 原方案的表述/方向 | 当前证据 | 应改成什么 |

| C9-2=Python 嵌入、C9-3=对接、C9-6=打包 | 专项计划的 C9-2=终端、C9-3=原生交互、C9-4=体验、C9-5=性能 [AC02] | 以专项计划为阶段 ID 事实源，建立旧编号映射，停止两套排期 |

| SSE 精确一次重放、未来新增心跳/续传 | 已有 seq 去重、重放和注释心跳；发布与游标提交有重复投递窗口 [AC05] | 描述为持久重放＋幂等去重，不承诺端到端所有副作用 exactly-once |
| 未来半年再做依赖扫描自动化 | CI 定义中已包含后端/前端依赖审计、契约与测试 [AC06] | 盘点缺哪些规则/覆盖/时效与豁免复核，不重新列“首次接入扫描” |
| 扩展能力矩阵，并把降级链列入未来功能 | 原稿的“能力矩阵扩展”有现成基础；当前也已有流式降级和 Schema 参数传递；embedding 另有边界 [AC07] | 保留有需求的增量；不把已有降级链重列为首次建设，区分配置、新协议与 embedding |

**判断**：这不是少量措辞问题。若不修正，团队会重复投入已有基础、错估桌面剩余量，并跳过当前更重要的前置保证。

## 3. 影响执行顺序的关键审查发现

### AC-R01｜共享副作用判定必须排在 Saga、重跑扩展和公开模板之前【P0】

**原方案**：§1.1 把失败节点重跑的副作用阻断列为完成；§3.2 计划增加补偿事务。

**Observed**：共享 `node_side_effect_reason` 识别 tool/human/部分 agent/iteration 子节点，其他非 agent 类型直接无阻断理由。重跑、评测和租约恢复使用该判定 [AC08]。

**Verified 离线反例**：一个配置为 HTTP POST 的有效 NodeSpec，返回 `reason=null`。本轮没有发送 HTTP 请求，也没有实际重跑外部操作；确认的是共享分类缺口，而非已发生重复写入事故。

**建议**：建立一处权威的执行效果/可重放声明，覆盖 HTTP、code、插件、引用子工作流和动态工具配置；区分只读、可幂等重放、有副作用、结果未知。不能给重跑、评测、恢复各补一套不同的 if。

**验收**：HTTP 写请求默认不可被当作安全只读重放；特例必须显式声明并验证幂等。三个调用入口共用矩阵，覆盖中断、参数/版本变化和“不知道外部操作是否已完成”。

### AC-R02｜稳定 SDK 发布前，补齐契约兼容的输入/输出方向【P0】

**Observed**：请求和响应复用同一 Schema 检查逻辑；required 和 enum 的演进检查未充分区分方向 [AC09]。

**Verified 离线反例**：
1. 响应 `id` 从必填变可选，兼容门禁未阻止；新响应 `{}` 被新 schema 接受，却被旧 schema 拒绝。
2. 响应枚举新增值，门禁未阻止；新值被旧的封闭枚举 schema 拒绝。是否允许扩展需明确客户端策略，不能笼统当成始终兼容。

**建议**：补输入/输出方向性规则及旧客户端消费测试；明确事件、DSL 和开放/封闭枚举的演进政策。保留现有契约生成和版本基线，不重建一套注册系统。

**验收**：请求增加必填、响应减少保证等反例被正确处理；真实旧版 SDK 能消费允许的新版响应；破坏性变化走版本迁移，不靠继续放宽校验。

### AC-R03｜桌面路线图需要“重定位剩余工作”，不是再实现一次壳【P0 文档/发布门】

专项计划 `docs/c9-desktop-tauri-plan.md:184` 和当前代码已比主方案靠前；但同一专项计划也明确保留干净机人工验收，签名与完整 updater 不等于已完成 [AC02]。

**保留**：终端、原生交互、崩溃恢复、首次接入体验。

**修订**：把剩余任务变为明确验收项：安装/卸载、无 Python/Node 环境启动、端口与进程树回收、数据目录升级、REST/SSE 真实连接、首次字体离线加载、失败界面与支持材料。CI job 存在不证明它最近产出了合格安装包。

**后置**：macOS/Linux、完整自动更新、继续材质/动效重写，除非有试点需求与签名发布责任人。

### AC-R04｜MCP catalog 批准与进程隔离必须分开【P1；公开分发前置】

**Observed**：MCP live client 绑定 owner task/执行连接表；stdio 启动会继承环境。catalog 的 filesystem grant 不能据此证明整个进程的文件系统权限已由 OS 隔离 [AC10]。

**建议**：优先做环境/凭据最小化、文件/网络权限、进程配额和退出回收；approved 版本、权限 diff 是供应链审查层，不替代运行隔离层。

**不建议原样采纳**：“live session 在 worker 间迁移”当作普通连接池优化。它涉及任务、子进程、在途调用、所有权和计费。先采用 owner 内复用、受控预热、从持久配置重连；真正迁移另立协议设计。

**验收**：被移交的是可持久化的任务/配置，而非假定可搬运的内存连接；不允许移交前后重复副作用；第三方 MCP 得不到无关环境凭据。此处是源级边界分析，不是漏洞复现。

### AC-R05｜SSE 优化不能破坏已有序号和终态语义【P1】

原方案 §6.3 的“关键事件优先推送”可能与单执行单调游标冲突：终态不能越过更早的持久事件。gzip/合并也可能影响持续 flush；本轮没有做网络性能测量。

**建议**：先压测断线、重复投递、Redis 故障、多个执行独立游标和慢消费者；优先级只能用于不破坏单执行顺序的调度。客户端应用状态以幂等消费恢复，不把传输去重扩大解释成业务动作恰好一次。

**验收**：发布后/游标提交前中断仍可恢复；无丢事件、无终态越序；测首事件和持续流延迟后才考虑压缩 [AC05]。

### AC-R06｜高级编排必须先给出确切语义【P2】

“OR-join 等待任意一个或多个”混合了 race、quorum、等待所有已激活分支等不同需求。它们的取消、失败和输出合并规则并不相同。

**建议顺序**：先选一个真实工作流，定义分支激活集合与 join 策略；随后考虑独立持久子执行和外部信号。通知机制不能替代持久 inbox、幂等身份、超时和恢复语义。

Saga 还依赖 AC-R01 的效果声明、补偿授权、重复补偿和结果未知处理。不要只新增一个 `saga_state` 表就声称具备业务事务保证 [AC04、AC08]。

### AC-R07｜性能建议需要从当前负载证据出发【P1 建基线，P2 具体方案】

SQLite c50 的历史创建时延，不能单独证明需要 PgBouncer、物化视图或 Redis 热缓存。500 节点的压测目标也不能未经核对就表述为硬上限或绝大多数用户需求。

**建议**：分开测 API 创建、队列等待、数据库锁/池等待、运行执行、SSE 交付以及画布交互；记录后端、数据规模、并发、机器与缓存状态。再决定索引、批处理、分区、缓存、布局 Worker 或 LOD。

**不先做**：WebGL 重写、第二套执行队列、分布式配置缓存。它们引入的权限/失效/恢复成本可能超过收益。现有持久队列和 Provider 缓存必须先被计入设计 [AC03、AC11]。

### AC-R08｜模板可优先，公开市场及支付应后置【P1 模板包；P2/P3 市场】

原方案把“发布到市场/评分”排在依赖与兼容性检查之前。对可执行工作流，这个顺序不合适。

**更小的增量**：先做受控模板包：固定 DSL/模型/MCP/插件依赖、所需权限、示例输入、预期成本区间、测试结果、许可证与校验摘要；导入前预检，安装后在可信样例上验证。

公开市场需要额外承担恶意内容、凭据/数据脱敏、供应链审查、撤回、滥用、举报和支持责任。付费市场还涉及结算/退款/税务/权利责任，不能算成几张表和一个 Stripe SDK。

### AC-R09｜CLI/SDK 值得做，但应按用户入口收缩【P1，有需求才升 P0】

缺少统一产品 CLI 不代表没有迁移/备份服务；已有服务应由薄 CLI 调用，而不是再写第二套运维逻辑。优先 `doctor`、配置检查、一个执行/结果命令；`restore/deploy` 默认需要预检、明确目标与确认。

SDK 先选一个实际需要的语言和调用场景：鉴权、提交、查询、取消、错误及 SSE 恢复。前端已有生成契约类型，可作为基础；不同时承诺 TypeScript/Python/Go/Java 全 API 覆盖 [AC01、AC06、AC12]。

**依赖**：AC-R02 先于稳定 SDK 对外发布；新客户端不得复制权限逻辑或默认对写请求盲重试。

### AC-R10｜依赖升级与工具替换应按风险/收益触发【P1 安全维护；P3 无证据换栈】

原稿中的“最新”版本判断、未来 LangGraph/MCP 主版本及若干工具替换没有本轮外部证据，不应变成固定年度任务。监测未来发布合理，承诺迁移未确认的版本不合理。

当前前端是 Vite SPA 和 FastAPI 后端；Server Functions、Turbopack、第二套类型检查器或格式工具不是版本号升级的自动收益。

**建议**：依据安全公告、停止支持、兼容性和可测收益触发升级；保留 lock 与现有 CI，单次升级设回退点。不把迁移成本包装成产品价值 [AC06、AC11]。

### AC-R11｜“端到端加密”与合规目标需要重写定义【P1 定义边界；实施按需求】

TLS、静态字段加密、KMS 和浏览器先加密并不是同一项保证。服务端/工具/模型若需要解密处理，就必须明确谁能看到明文、密钥由谁控制；不能笼统称为端到端加密。

桌面 localhost HTTP 与公网 HTTPS 也不是同一部署档位。当前 HSTS 明确是可配置的公网部署能力，不能统一强制到本机链路 [AC13]。

差分隐私应有实际统计发布、邻接关系与隐私预算需求；SOC 2/ISO 等需要组织控制和外部过程，不能按实现几个 API 即验收。当前没有成本/认证可行性证据。

### AC-R12｜优先级、成本和资源模型需要从清单变为承诺【P0 排期修订】

原稿有“子项 P1/全节 P2”、SDK 在不同位置为 P0/P1、C9 阶段互相矛盾等情况，未明确局部排序与全局优先级的区别。

3–5 名核心工程师之外又列产品、设计、DevRel、写作、安全；这些人员尚未由用户确认。固定美元月费缺少配置、流量、模型费用、区域与支持人力依据，只能作为待验证假设，不是预算。

**建议**：只保留一个全局 backlog；每项写使用者、MVP、依赖、有效人日、owner、验收、放弃条件。基础设施成本用“固定资源＋调用/存储/出口＋备份/监控＋支持”分解，再按实测量和实际报价估算。

## 5. 建议替换进原方案的执行主线

### 5.1 产品范围

**Derived 推荐定位**：面向开发者与内部自动化团队的可视化工作流编排/执行平台，先把 Windows 可信自托管与可审核集成做好。

首个完整场景可以是“有明确输入、受控 MCP 工具、人工审批点、可追溯结果”的内部自动化任务。具体业务由使用者选定，不默认所有人都需要市场、多人同时编辑或跨平台桌面。

### 5.2 第一批可执行工作包

### 5.3 90 天容量模型

**Assumed**：两名工程师，12 周×5 天×70% 有效交付，约 84 人日；建议承诺不超过 65–70 人日，其余留给集成、回归和验收。不把全部候选叠加进去。

|---|---|---|

| 31–60 天 | AC-T05 二选一，AC-T06 与一个 AC-T07 场景；补首次接入文档 | 不同时做四语言 SDK、多个渠道和企业身份协议 |
| 61–90 天 | 真实试点；AC-T08；补最影响任务完成的故障/诊断点；根据证据决定下一季度 | 不因阶段末尾“还有清单”就压缩安全/兼容验收 |

若主要用户是 API 集成方，选择 SDK；若是本地桌面/自托管团队，优先 doctor/配置预检和桌面收口。两条路线可以共享基础，不必首个季度全部做完。

**单人版本**：12 周约 42 有效人日，建议仅承诺 32–35 人日。默认选择 AC-T01~T04＋AC-T07，一个真实场景沿用现有 UI/REST/脚本；按表中上界合计 33 人日。CLI/SDK/模板不再一并承诺：只有扣除实际消耗和缓冲后仍覆盖所选包的上界才加入，否则缩减明确 MVP、二选一或顺延。不能靠各项区间下界承诺“入口和场景都做”。市场、CRDT、复杂编排顺延。

**组合资源提示**：这是 AgentCanvas 独占人力的假设。若同一团队还维护 `E:/agent1` 或其他项目，不能同时承诺每个项目各自的双人 90 天计划，需选主项目或延长日历时间。

### 5.4 3–6 月与 6–18 月进入条件

- **3–6 月**：只有重复使用的模板/集成需求出现后，扩大受控模板库、Provider/MCP 和运行诊断；并发或画布性能必须先由基线证明是瓶颈。
- **企业协作**：出现真实冲突/成员生命周期需求，才投入 CRDT、SCIM 等；可保留执行 SSE、另外为编辑协作设计通道，不全局替换协议。
- **复杂编排**：有不能被当前模式清晰表达的案例，并完成 AC-T02/03 后，再选择一种 join/持久子执行/信号能力。Saga 更后置。
- **SaaS/市场**：需明确用户、运营者、供应链与隔离、投诉/撤回/删除、计费对账及支持成本；不是表结构完成即上线。
- **跨平台/自动更新**：有目标用户、测试设备和签名/公证/发布责任人；按平台分别验收，不由 Windows 结果外推。

## 6. 应补入方案的验收标准

| 主题 | 推荐验收内容 | 不能用来替代的证据 |
|---|---|---|
| 首次价值 | 干净环境完成一个从导入/配置到结果的任务，记录时间与阻塞点 | README 操作步骤存在、截图好看 |
| 安全重放 | 各入口按同一效果策略执行；变化参数/版本不能复用旧授权；不确定结果不盲重试 | 单个 helper 单测或节点类型名单 |
| 公共契约 | 旧客户端真实消费新版响应/事件；方向性边界有反例测试 | 生成类型没有 diff |
| 桌面 | 安装/启动/升级/失败/进程回收/数据保留清单逐项记录 | Tauri 源码存在或 CI job 定义存在 |
| 流恢复 | 重复/断线/Redis 故障/多执行/终态顺序 | 只有正常 SSE 流用例 |
| 向量迁移 | 维度、数量、租户过滤、删除、检索行为与回滚说明 | “两个实现都叫 sql” |
| 性能 | 同机器/数据/并发/缓存状态对比，p50/p95/p99＋错误率/内存 | 沿用历史单次数字或只看平均值 |
| 集成生态 | 真实鉴权、stream/tool/schema、费用、取消、错误；信任边界明确 | 可选择 Provider 名称或 catalog 审核通过 |
| 商业化 | 使用者确实完成任务；价格/计费/支持假设有依据 | 新增节点数、模板数、注册量本身 |

性能、首次接入和业务目标由试点确定；可以提出目标，但不得把它们提前标成已达成。覆盖率作为风险可见性辅助指标，不作为“补到 90% 就成熟”的唯一条件。
