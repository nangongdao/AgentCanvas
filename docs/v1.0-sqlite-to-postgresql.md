# AgentCanvas v1.0 SQLite to PostgreSQL Migration

This is the supported offline cutover from a v0.x single-host SQLite/Chroma
deployment to the v1.0 PostgreSQL/pgvector cluster. It preserves relational
records, chat memory, durable checkpoints, uploads, workspace files, and
Chroma-backed RAG vectors. Redis coordination state is intentionally rebuilt.
SQLite SQL-vector rows are outside the supported source format and must be
exported or rebuilt before the cutover.

The migration is fail-closed and requires downtime. Practice it against a copy
and record source/target counts before scheduling the production cutover.

## 1. Stop and back up v0.x

Stop API and execution processes so `app.db`, `checkpoints.db`, Chroma, uploads,
and workspace files form one consistency point. With the v1.0 code and the
legacy data directory mounted read/write only for the backup command:

```bash
cd backend
python -m uv run python -m app.services.backup backup \
  ../backups/pre-v1.0.tar.gz --data-dir /srv/agentcanvas-v0/data
sha256sum ../backups/pre-v1.0.tar.gz > ../backups/pre-v1.0.tar.gz.sha256
```

Keep the original directory offline. Restore the checksummed archive into a new
empty staging directory; never upgrade the only copy:

```bash
mkdir -p /srv/agentcanvas-v1-staging
env -u DATABASE_URL python -m uv run python -m app.services.backup restore \
  ../backups/pre-v1.0.tar.gz --data-dir /srv/agentcanvas-v1-staging --force
```

Use the same `SECRET_KEY` in v1.0 or encrypted Provider/MCP credentials cannot
be decrypted. Rotate that key only through the separate credential procedure in
the operations runbook.

## 2. Upgrade the staging SQLite schema

Upgrade the restored copy to the current v1.0 head. The source copy must reach
`0030_callback_activation_boundary` (which includes `0024_document_chunks`) before
relational data is copied:

```bash
export APP_DATA_DIR=/srv/agentcanvas-v1-staging
export DATABASE_URL=sqlite+aiosqlite:////srv/agentcanvas-v1-staging/app.db
export APP_PROCESS_ROLE=all
export STARTUP_MIGRATIONS=true
python -m uv run python -m app.services.migrate
```

This step changes only the staging copy. Do not start an API or worker against
it. Before continuing, inspect the source vector table:

```bash
sqlite3 /srv/agentcanvas-v1-staging/app.db \
  'select count(*) as document_chunks from document_chunks;'
```

The relational copy requires this count to be zero. v0.x installations that
stored vectors in SQLite SQL rows are not copied by this release command; export
those vectors into the supported Chroma source format or rebuild the index
before cutover. Chroma-backed installations continue with the dedicated vector
step below.

## 3. Prepare an empty PostgreSQL target

Install pgvector, create a new empty database, and run the v1.0 migration service
once. The target may contain Alembic-created tables but no application rows:

```bash
export DATABASE_URL='postgresql+asyncpg://agentcanvas:REDACTED@db:5432/agentcanvas'
export VECTOR_BACKEND=pgvector
export APP_PROCESS_ROLE=all
export STARTUP_MIGRATIONS=true
python -m uv run python -m app.services.migrate
```

Do not run `bootstrap` yet. The relation copy refuses a non-empty target so an
accidental merge cannot duplicate or overwrite tenant data.

## 4. Copy relational data

```bash
python -m uv run python -m app.services.migrate_sqlite \
  --source /srv/agentcanvas-v1-staging/app.db
```

The command requires a `postgresql+asyncpg` target at the current migration
head, copies tables in foreign-key order in one target transaction, orders
self-referential executions/comments parent-first, resets PostgreSQL sequences,
and verifies every table count. It deliberately rejects non-empty
`document_chunks`; vectors use the dedicated two-pass Chroma-to-pgvector
migration below.

## 5. Copy checkpoints and vectors

No execution worker may run during these commands:

```bash
python -m uv run python -m app.services.migrate_checkpoints \
  --source /srv/agentcanvas-v1-staging/checkpoints.db
python -m uv run python -m app.services.migrate_vectors \
  --source /srv/agentcanvas-v1-staging/chroma
```

Checkpoint import is idempotent and verifies every `waiting_approval`. Vector
import performs a complete no-write preflight, then replaces each document under
a durable row lock and verifies final chunk counts. Any missing source vector,
knowledge-base mismatch, filename mismatch, or chunk-count mismatch aborts the
cutover.

Copy `uploads/` and `workspace/` from staging into the new empty application-data
volume. Keep the Chroma directory offline until PostgreSQL retrieval and restore
drills pass.

## 6. Start and verify v1.0

Set production roles to `STARTUP_MIGRATIONS=false`, configure Redis, retain the
same `SECRET_KEY`, run the idempotent `bootstrap` service, and start the 2 API +
2 worker topology.

Require:

- `/api/meta` reports version `1.0.0`, PostgreSQL, and pgvector.
- `/readyz` is ready on both API replicas at migration
  `0030_callback_activation_boundary`.
- Source and target counts match for workflows, versions, executions, events,
  users, projects, knowledge bases, documents, chat, evaluation, and audit rows.
- A preserved `waiting_approval` resumes after a full runtime restart.
- A known RAG query returns the same leading document through a second API.
- A v1.0 backup restores into a distinct empty database/data directory and the
  restore drill passes.

## 7. Rollback boundary

Before traffic is admitted, rollback means stopping v1.0 and restarting the
untouched v0.x directory. After v1.0 accepts writes, do not copy data backward.
Stop all writers and restore either the pre-v1.0 archive for a full rollback or a
verified v1.0 PostgreSQL archive into a new target. Never downgrade the live
schema or overwrite either source in place.
